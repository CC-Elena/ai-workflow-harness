AI Coding 能力演进下的 Harness 架构设计

随着 Claude Code、Codex 等 AI 编程工具能力持续提升，代码库级别的开发框架如何演进？
本文系统阐述 Harness 的架构设计原则、模块取舍策略与实施路线图。

2026年6月 架构设计 · AI 编程 · 工程实践
1

核心原则：模型能力边界外扩时，每一层都需要重新评估

核心逻辑

AI 编程模型的能力边界正在快速外扩。Harness 的每一层架构设计都需要持续审视：哪些模块已被模型能力覆盖而变得冗余，哪些模块反而因模型能力增强而价值凸显。框架的定位应向上游迁移——将模型已经能胜任的工作委托给它，聚焦于只有项目级上下文才能决策的环节。

基线（2024-2025）
AI Coding 模型的能力边界：能编写单个函数，跨文件重构能力有限
现状（2026）
能自主进行多文件重构、执行基本规划、运行代码并自我纠错
趋势（2027+）
能长时间自主工作（16h+），进行复杂方案评估与多维度权衡

若 Harness 始终维持在相同层级做相同的事，其边际价值将随模型能力提升而递减。每一次模型能力的跃迁，都意味着框架内某些模块可以卸除，某些模块反而更加关键。

2

可卸除的模块：模型已经能自行完成的职责

随着 Claude Code / Codex 能力提升，以下职责模型已经能可靠地自行完成，框架层可以卸除或降级：

模块 原框架职责 现状分析
降级代码质量检查 集成 linter、代码风格检查、模式匹配校验 AI 原生生成的代码质量已经足够高，语法和风格问题大幅减少。建议降级为可选的最后一道防线，而非流水线的必经阶段。
卸除步骤级任务分解 将功能需求拆分为 5-10 个微步骤，逐一调度执行 当前模型具备自主规划能力：给定中等粒度的任务，可自行拆解、执行、纠错。

结论：Plan 粒度从「步骤级」提升至「阶段级」，每个阶段内部细节由模型自行处理。
降级错误恢复 检测执行异常、分类错误类型、决策重试策略 模型在遇到编译或运行时错误时，已能自行分析、定位并修复。框架只需关注超过阈值仍未恢复的异常情况，而非每次编译错误都介入。
3

不可替代的核心模块：框架最持久的价值所在

以下能力是当前 AI 编程工具的短板，也是 Harness 框架最不可替代的差异化价值：

价值 1：Spec → Plan 的结构化翻译

这是框架最核心的一层。

AI 工具的「边做边想」模式在需求模糊时会产生大量无效探索。Plan 作为需求到代码之间的桥梁，其价值随模型执行能力的增强而递增——因为其余环节模型都能自行完成，唯独「明确要构建什么」这一决策环节，模型的输出质量完全取决于上游输入的精准度。

原始需求：「构建一个支持 CSV 导出的报表页面」 直接交由 AI 编程工具：边实现边理解需求，可能在方向选择上消耗大量时间 经过 Harness Plan 层： 1. 生成结构化 Plan（数据模型 → API 设计 → 前端组件 → 导出逻辑） 2. 开发者审阅并确认方案 3. 将 Plan 作为上下文交由 AI 编程工具执行

Harness 将这一层固化为显式、可审阅、可版本管理的 Plan 文档，而非依赖 prompt 的临时描述。

价值 2：项目级知识的持续积累

AI 编程工具每次对话从零开始，无法感知项目的长期上下文：

  • 历史架构决策及背后的原因
  • 特定模块的隐含约束（时序要求、并发限制等）
  • 同一功能的多个实现版本并存及其兼容性要求

Harness 将这些知识编码至 Plan 模板、约束规则和知识库中，而非依赖对话上下文（会话结束后即丢失）。

经过一段时间积累后，任何开发者使用 Harness 启动新任务，框架都能自动注入该项目的所有历史决策和已知陷阱。这是直接使用 AI 编程工具无法获得的长期收益。

价值 3：Spec 的自动化验收

AI 编程工具能编写代码和测试，但它不会主动校验 Spec 中的每一条需求是否均被实现和验证。

Harness 在每个 Plan 执行完毕后，自动执行 Spec 逐条验收：

需求点 1: 「导出按钮位于表格右上角」 → 检查对应组件是否存在 → ✅ 需求点 2: 「CSV 文件编码为 UTF-8 BOM」 → 检查导出函数是否包含 BOM 头 → ❌ 缺失 需求点 3: 「超过 10 万行数据时显示进度条」 → 未实现 → ❌ 未通过验收

这不是模型做不到的事情，而是模型不会主动做的事情。Harness 将这层保证固化为流水线的强制环节。

价值 4：架构一致性的全局守护

项目规模增大时，AI 编程工具倾向于做出局部最优决策——它不知道数个模块之外已经存在功能相同的工具函数或组件。

Harness 在 Plan 阶段注入架构约束：

  • 新增工具函数前，先检索 codebase 中是否已有等价实现
  • API 路径必须符合统一的命名约定
  • 新组件必须遵循既定的目录结构规范

在执行阶段再进行验证，确保约束落地。这是 AI 编程工具不具备的跨模块视野。

4

模型能力增强带来的全新机会

模型能力的跃迁使一些以往成本过高或技术上不可行的架构模式变得可行。以下模块是 Harness 应该主动纳入的新能力：

新能力 1：Plan 方案的多版本对比与选优

以往：模型生成代码的质量不足以支撑 A/B 方案的公平对比——两个版本都可能存在大量问题。

现在：模型代码生成质量已达到可进行双方案并行实现的水平。

需求输入 │ ├→ Planner 生成 Plan A（方案：REST API 模式） ├→ Planner 生成 Plan B（方案：GraphQL 模式） │ ├→ AI 编程工具同时实现 A 和 B │ （各自完成代码编写、测试、基准数据收集） │ ├→ 多维对比：性能 / 可维护性 / 代码体积 / 测试覆盖率 │ └→ 择优合并至主干分支

此前因人力成本过高而难以推行的双方案对比模式，现在已具备工程可行性。

新能力 2：Plan 的多 Agent 并行审阅

以往：Plan 由人工审阅，或未经审阅直接执行。

现在：模型的推理能力已达到可审阅 Plan 的水平。

Planner 产出 Plan │ ├→ Reviewer Agent（审阅 Agent） │ 审阅 Plan，标注风险点、逻辑漏洞、边界遗漏 │ ├→ Explorer Agent（探测 Agent） │ 检索现有 codebase，检查 Plan 与既有实现的冲突 │ ├→ Test Agent（测试 Agent） │ 根据 Plan 预生成关键验收测试用例 │ └→ 汇聚反馈，修正 Plan → 确认后进入执行阶段

这是Multi-Agent 探索层的核心思想——多个 Agent 并行从不同维度审阅 Plan，汇聚后产出更高质量的方案，再进入 Planner-Executor 串行执行回路。

新能力 3：执行过程的可观测性

以往：Harness 只能观测到模型输出的最终产物（代码文件）。

现在：模型的长时间自主运行能力意味着：需要感知执行过程中的决策路径。

Harness 应提供执行过程的决策可视化，展示的并非模型编写了什么代码，而是：

当前阶段：Phase 2/3 - 支付模块对接 已放弃方案：直接调用支付 SDK → 放弃原因：QPS 限制不满足业务要求 当前方案：通过消息队列异步处理，削峰填谷 预计剩余时间：基于历史相似任务估算 风险提示：支付回调时序可能存在陷阱（知识库记录显示曾在 2026.03 遇到过）

目标架构：Harness 的最终形态

┌───────────────────────────────────────────────────┐ │ Harness 框架（核心价值层） │ │ │ │ 用户需求 → Spec → Plan 生成 → 方案对比 │ │ │ │ │ ├→ Plan 审阅（Multi-Agent 并行探索层） │ │ │ │ │ ├→ 架构约束注入 + 项目知识库注入 │ │ │ │ │ ├→ ┌──────────────────────────┐ │ │ │ │ AI 编程工具执行 │ ← 模型发挥作用 │ │ │ │（自主规划 + 编写 + 修复） │ │ │ │ └──────────────────────────┘ │ │ │ │ │ ├→ Spec 验收 + 架构一致性检查 │ │ │ │ │ └→ 产物归档 + Plan 写入知识库 │ └───────────────────────────────────────────────────┘ Harness 的定位不是「AI 编程工具的高级封装」， 而是项目管理、知识积累、质量保证的工程基础设施层。 AI 编程工具是执行引擎，Harness 是控制面和治理层。
设计哲学

AI 编程工具大幅降低了编写代码的边际成本。Harness 框架的目标是降低「写出正确代码」的保证成本。

对齐 Plan → 检查规范 → 验收 Spec → 积累知识。这四项能力是当前 AI 编程工具均未充分覆盖的领域，是 Harness 框架存在的根本理由。

能力维度 AI 编程工具（原生能力） Harness 框架（增强能力）
规划可见性 黑盒，隐式推理 白盒，显式 Plan 文档
规划复用 每次从零推理 历史 Plan 可复用、可进化
质量门禁 无结构性检查 每个阶段明确准入/准出条件
领域知识注入 依赖 prompt 质量 框架内置项目规范与架构约束
审计追溯 不可追溯 Spec → Plan → 实现 → 验收 全链路可回溯
断点续传 依赖对话历史，会话丢失则不可恢复 每个阶段产物持久化，任意阶段可恢复执行

实施路线图：从当前架构到目标架构

适用场景判定

以下场景中，引入 Harness 框架层将产生显著收益：

  • 多人协作项目，需要通过 Plan 文档对齐开发方向（多个开发者使用 AI 工具独立工作时，产生的方案可能互相冲突）
  • 存在强架构约束的项目（特定的分层规则、命名规范、依赖注入模式需要强制执行）
  • 需要可追溯的决策记录（团队变动时，新人需要理解「为什么这个模块这样设计」）
  • Spec 到代码之间存在大量设计决策（需要「生成选项 → 对比评估 → 选择最优」的闭环流程）

分阶段实施路径

第一阶段 · 建立显式 Plan 文档体系
目标：将隐式的规划过程固化为显式的、可版本管理的文档，存入代码库，随项目演进持续更新。完成这一步后，每次 AI 辅助开发都从确定性的 Plan 出发。
第二阶段 · 建立质量门禁
目标：在 Plan → 实现 → 测试的每个阶段之间，加入不可跳过的结构化检查点。加载架构约束规则，自动验证产出物是否满足准出条件。
第三阶段 · 建立项目知识库
目标：将历史架构决策、已知陷阱、架构演进记录结构化存储。Harness 在生成 Plan 时自动检索相关历史知识，注入约束和建议。
第四阶段 · 引入 Multi-Agent 探索层（持续演进）
目标：在 Spec 完成后、Plan 开始前，插入并行 Agent 探索环节。多个 Agent 从不同维度审阅 Spec 和 Plan 初稿，汇聚反馈后修正 Plan，再进入 Planner-Executor 串行执行回路。
设计决策注意事项

1. 避免过度工程：单人开发、项目简单、需求明确的场景，直接使用 AI 编程工具进行对话式开发效率更高，无需引入 Harness 框架层。

2. 不要与模型竞争代码编写能力：那是 AI 编程工具的强项。Harness 应聚焦于模型不擅长的事情——治理、约束、验收和知识积累。

3. 保持架构敏捷性：每当模型发布新能力，都需要重新评估 Harness 的每一层——这个模块是否仍然需要？是否有更轻量的替代方案？
