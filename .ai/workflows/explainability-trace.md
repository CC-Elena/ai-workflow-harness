# 可解释性与执行追踪协议

本文档定义 AI Workflow Harness 的解释证据和执行追踪要求。目标是让任何一次 AI 执行都能被审查者理解：为什么这么做、依据是什么、验证是否真实、风险在哪里。

## 1. 可解释性的定义

一次执行可解释，必须满足：

1. 每个关键决策都能追溯到 Spec、上下文、Skill、验证或用户确认。
2. 每个修改文件都有对应任务。
3. 每个验收标准都有验证方式或跳过原因。
4. 每个失败都有原因、处理动作和剩余风险。
5. 每个评估分数都有证据。

## 2. 追踪维度

| 维度 | 必填内容 | 记录位置 |
|------|----------|----------|
| Intent Trace | 用户需求、PRD、目标、非目标 | `prd.md`、`spec.md` |
| Decision Trace | 关键取舍、范围控制、人工确认 | `tasks.md`、`run-record.md` |
| Context Trace | 读取了哪些上下文和 Skill | `tasks.md`、`run-record.md` |
| Change Trace | 修改了哪些文件以及原因 | `run-record.md` |
| Verification Trace | 运行了哪些验证和结果 | `verification-record.md` |
| Evaluation Trace | 分数、阻断项、投产判断 | `evaluation-summary.md` |
| Learning Trace | RCA 和反哺项 | `rca.md`、`pilot-retrospective.md` |

## 3. 关键决策记录格式

```markdown
## Decision Trace

| 决策 | 选项 | 选择 | 依据 | 风险 | 是否人工确认 |
|------|------|------|------|------|--------------|
| 数据来源 | 静态常量 / 文件扫描 / API | 静态常量 | MVP 不做平台能力 | 后续需手动维护 | 否 |
```

## 4. 修改解释格式

```markdown
## Change Trace

| 文件 | 任务 | 修改原因 | 对应验收 | 风险 |
|------|------|----------|----------|------|
| `app/example.tsx` | T1 | 增加筛选控件 | AC-1 | 低 |
```

## 5. 验证解释格式

```markdown
## Verification Trace

| 验收标准 | 验证方式 | 结果 | 证据 | 跳过原因 |
|----------|----------|------|------|----------|
| 移动端无溢出 | Playwright 390px 检查 | Pass | screenshot path | |
```

## 6. 评分解释格式

评估分数必须给出证据，不允许只写总分。

```markdown
| 维度 | 得分 | 证据 | 扣分原因 | 改进项 |
|------|------|------|----------|--------|
| 验证质量 | 4 | `verification-record.md` | 缺少失败样本 | 补 RCA 案例 |
```

## 7. 不可接受的解释

以下记录不合格：

1. “已完成”但没有修改文件列表。
2. “验证通过”但没有命令或截图证据。
3. “按最佳实践实现”但没有指向本仓库规则。
4. “风险较低”但没有说明影响范围。
5. “不需要 RCA”但没有说明未触发的原因。

## 8. 审查问题清单

Review 时优先问：

1. 这次执行的可信源是什么？
2. 修改是否能逐项映射到任务？
3. 是否读了必要上下文和 Skill？
4. 是否有未解释的范围扩大？
5. 验证结果是否可复现？
6. 评分是否有证据？
7. 是否有应触发但未触发的 RCA？
