# 文档共创工作流 (Doc Co-Authoring Workflow)

本 Skill 提供了一个结构化的工作流，引导用户进行协作文档创建。充当积极的向导，带领用户通过三个阶段：上下文收集、完善与结构化、读者测试。

## 何时提供此工作流

**触发条件:**
- 用户提到写文档："写个文档", "起草提案", "创建规范", "写一下"
- 用户提到特定文档类型："PRD", "设计文档", "决策文档", "RFC"
- 用户似乎要开始一项实质性的写作任务

**初始提议:**
向用户提议一个用于共同撰写文档的结构化工作流。解释这三个阶段：

1. **上下文收集 (Context Gathering)**: 用户提供所有相关上下文，同时 Claude 提出澄清问题
2. **完善与结构化 (Refinement & Structure)**: 通过头脑风暴和编辑逐节构建
3. **读者测试 (Reader Testing)**: 用一个新的 Claude（无上下文）测试文档，以便在其他人阅读之前发现盲点

解释这种方法有助于确保文档在其他人阅读时（包括当他们将其粘贴到 Claude 中时）效果良好。询问他们是否想尝试此工作流，或者更喜欢自由形式的工作。

如果用户拒绝，则进行自由形式的工作。如果用户接受，进入阶段 1。

## 阶段 1：上下文收集 (Context Gathering)

**目标:** 缩小用户所知与 Claude 所知之间的差距，以便后续提供智能指导。

### 初始问题

首先询问用户有关文档的元上下文：

1. 这是什么类型的文档？（例如：技术规范、决策文档、提案）
2. 主要受众是谁？
3. 当有人阅读时，期望产生什么影响？
4. 有没有要遵循的模板或特定格式？
5. 还有其他约束或上下文需要知道吗？

告知他们可以用简写回答，或者以最适合他们的方式倾倒信息。

**如果用户提供模板或提到文档类型:**
- 询问他们是否有模板文档可以分享
- 如果他们提供共享文档的链接，使用适当的集成来获取它
- 如果他们提供文件，读取它

**如果用户提到编辑现有的共享文档:**
- 使用适当的集成读取当前状态
- 检查没有 alt 文本的图像
- 如果存在没有 alt 文本的图像，解释当其他人使用 Claude 理解文档时，Claude 将无法看到它们。询问是否要生成 alt 文本。如果是，请他们将每个图像粘贴到聊天中以生成描述性 alt 文本。

### 信息倾倒 (Info Dumping)

回答完初始问题后，鼓励用户倾倒他们拥有的所有上下文。请求诸如以下信息：
- 项目/问题的背景
- 相关团队讨论或共享文档
- 为什么不使用替代方案
- 组织上下文（团队动态、过去的事故、政治）
- 时间紧迫性或限制
- 技术架构或依赖关系
- 利益相关者的担忧

建议他们不要担心组织——尽管倒出来。提供多种提供上下文的方式：
- 意识流式的信息倾倒
- 指出要阅读的团队频道或帖子
- 链接到共享文档

**如果集成可用**（例如：Slack, Teams, Google Drive, SharePoint 或其他 MCP 服务器），提到可以使用这些直接拉取上下文。

**如果未检测到集成且在 Claude.ai 或 Claude app 中:** 建议他们在 Claude 设置中启用连接器，以允许直接从消息传递应用程序和文档存储中拉取上下文。

告知他们一旦完成了初始倾倒，将会提出澄清问题。

**在上下文收集期间:**

- 如果用户提到团队频道或共享文档：
  - 如果集成可用：告知他们现在将读取内容，然后使用适当的集成
  - 如果集成不可用：解释缺乏访问权限。建议他们在 Claude 设置中启用连接器，或者直接粘贴相关内容。

- 如果用户提到未知的实体/项目：
  - 询问是否应搜索连接的工具以了解更多
  - 在搜索前等待用户确认

- 当用户提供上下文时，跟踪正在了解的内容和仍不清楚的内容

**提出澄清问题:**

当用户表示他们已完成初始倾倒（或在提供了大量上下文后），提出澄清问题以确保理解：

根据上下文中的空白生成 5-10 个编号的问题。

告知他们可以用简写回答（例如："1: 是, 2: 见 #channel, 3: 不，因为向后兼容"），链接到更多文档，指出要阅读的频道，或者只是继续信息倾倒。无论哪种对他们最有效。

**退出条件:**
当问题表明已经理解——当可以询问边缘情况和权衡而无需解释基础知识时，已收集足够的上下文。

**过渡:**
询问他们在此阶段是否还有更多上下文想要提供，或者是否到了起草文档的时候。

如果用户想添加更多，让他们添加。准备好后，进入阶段 2。

## 阶段 2：完善与结构化 (Refinement & Structure)

**目标:** 通过头脑风暴、策划和迭代完善，逐节构建文档。

**给用户的指示:**
解释文档将逐节构建。对于每一节：
1. 将询问有关包含什么内容的澄清问题
2. 将头脑风暴 5-20 个选项
3. 用户将指示保留/删除/合并哪些内容
4. 该节将被起草
5. 将通过精准编辑进行完善

从未知数最多的部分开始（通常是核心决策/提案），然后处理其余部分。

**章节排序:**

如果文档结构清晰：
询问他们想从哪一节开始。

建议从未知数最多的部分开始。对于决策文档，通常是核心提案。对于规范，通常是技术方法。摘要部分最好留到最后。

如果用户不知道他们需要什么章节：
根据文档类型和模板，建议 3-5 个适合文档类型的章节。

询问这个结构是否可行，或者他们是否想要调整它。

**一旦结构达成一致:**

创建带有所有章节占位符的初始文档结构。

**如果可以访问 Artifacts:**
使用 `create_file` 创建一个 artifact。这为 Claude 和用户提供了一个工作的脚手架。

告知他们将创建带有所有章节占位符的初始结构。

创建带有所有章节标题和简短占位符文本（如"[待编写]"或"[内容在此]"）的 artifact。

提供脚手架链接并指示是时候填写每一节了。

**如果无法访问 Artifacts:**
在工作目录中创建一个 markdown 文件。适当命名（例如：`decision-doc.md`, `technical-spec.md`）。

告知他们将创建带有所有章节占位符的初始结构。

创建带有所有章节标题和占位符文本的文件。

确认文件名已创建并指示是时候填写每一节了。

**对于每一节:**

### 步骤 1：澄清问题

宣布将开始 [章节名称] 部分的工作。提出 5-10 个关于应包含内容的澄清问题：

根据上下文和章节目的生成 5-10 个具体问题。

告知他们可以用简写回答或仅指示涵盖哪些重要内容。

### 步骤 2：头脑风暴

对于 [章节名称] 部分，根据章节的复杂性，头脑风暴 [5-20] 个可能包含的内容项。寻找：
- 可能被遗忘的共享上下文
- 尚未提及的角度或考虑因素

根据章节复杂性生成 5-20 个编号选项。最后，如果有更多内容想要添加，提供更多头脑风暴选项。

### 步骤 3：策划

询问应该保留、删除或合并哪些点。请求简要理由以帮助了解下一节的优先级。

提供示例：
- "保留 1,4,7,9"
- "删除 3 (重复 1)"
- "删除 6 (受众已经知道这个)"
- "合并 11 和 12"

**如果用户提供自由形式的反馈**（例如："看起来不错"或"我喜欢大部分但..."）而不是编号选择，提取他们的偏好并继续。解析他们想要保留/删除/更改的内容并应用它。

### 步骤 4：差距检查

根据他们选择的内容，询问 [章节名称] 部分是否遗漏了任何重要内容。

### 步骤 5：起草

使用 `str_replace` 将此节的占位符文本替换为实际起草的内容。

宣布现在将根据他们的选择起草 [章节名称] 部分。

**如果使用 Artifacts:**
起草后，提供 artifact 链接。

请他们通读并指示要更改的内容。注意具体说明有助于后续章节的学习。

**如果使用文件 (无 Artifacts):**
起草后，确认完成。

告知他们 [章节名称] 部分已在 [文件名] 中起草。请他们通读并指示要更改的内容。注意具体说明有助于后续章节的学习。

**给用户的关键指示 (在起草第一节时包含):**
提供一个提示：不要直接编辑文档，而是请他们指示要更改的内容。这有助于学习他们未来章节的风格。例如："删除 X 项目符号 - 已被 Y 覆盖" 或 "让第三段更简洁"。

### 步骤 6：迭代完善

当用户提供反馈时：
- 使用 `str_replace` 进行编辑（切勿重新打印整个文档）
- **如果使用 Artifacts:** 每次编辑后提供 artifact 链接
- **如果使用文件:** 仅确认编辑已完成
- 如果用户直接编辑文档并要求阅读：在心里记下他们所做的更改，并在未来章节中牢记（这显示了他们的偏好）

**继续迭代** 直到用户对该节满意。

### 质量检查

连续 3 次迭代无实质性更改后，询问是否可以在不丢失重要信息的情况下删除任何内容。

当章节完成时，确认 [章节名称] 已完成。询问是否准备好进入下一节。

**由于所有章节重复此过程。**

### 接近完成

当接近完成时（80%+ 的章节完成），宣布打算重读整个文档并检查：
- 章节之间的流畅性和一致性
- 冗余或矛盾
- 任何感觉像"垃圾"或通用填充物的内容
- 是否每一句话都有分量

阅读整个文档并提供反馈。

**当所有章节都已起草和完善:**
宣布所有章节已起草。表示打算再审查一次完整的文档。

审查整体连贯性、流畅性、完整性。

提供任何最终建议。

询问是否准备好进入读者测试，或者他们是否想要完善其他内容。

## 阶段 3：读者测试 (Reader Testing)

**目标:** 用一个新的 Claude 实例（无上下文干扰）测试文档，验证其对读者的有效性。

**给用户的指示:**
解释现在将进行测试，看看文档是否真的对读者有效。这能捕捉盲点——对作者来说有意义但可能使其他人困惑的事情。

### 测试方法

**如果可以访问子 Agent (例如：在 Claude Code 中):**

无需用户参与直接执行测试。

### 步骤 1：预测读者问题

宣布打算预测读者在尝试发现此文档时可能会问什么问题。

生成 5-10 个读者实际上会问的问题。

### 步骤 2：使用子 Agent 测试

宣布将使用一个新的 Claude 实例（无此对话的上下文）测试这些问题。

对于每个问题，调用一个子 Agent，只提供文档内容和问题。

总结读者 Claude 对每个问题的回答是对还是错。

### 步骤 3：运行额外检查

宣布将执行额外检查。

调用子 Agent 检查模糊性、错误假设、矛盾。

总结发现的任何问题。

### 步骤 4：报告和修复

如果发现问题：
报告读者 Claude 在具体问题上遇到困难。

列出具体问题。

表示打算修复这些差距。

回环到完善阶段以修复有问题的章节。

---

**如果无法访问子 Agent (例如：claude.ai Web 界面):**

用户需要手动进行测试。

### 步骤 1：预测读者问题

询问人们在尝试发现此文档时可能会问什么问题。他们会在 Claude.ai 中输入什么？

生成 5-10 个读者实际上会问的问题。

### 步骤 2：设置测试

提供测试说明：
1. 打开一个新的 Claude 对话: https://claude.ai
2. 粘贴或分享文档内容（如果使用启用了连接器的共享文档平台，提供链接）
3. 问读者 Claude 生成的问题

对于每个问题，指示读者 Claude 提供：
- 答案
- 任何模糊或不清楚的地方
- 文档假设已知哪些知识/上下文

检查读者 Claude 是否给出正确答案或误解了任何内容。

### 步骤 3：额外检查

还要问读者 Claude：
- "这篇文档中有什么对读者来说可能模糊或不清楚的？"
- "这篇文档假设读者已经具备哪些知识或上下文？"
- "是否有任何内部矛盾或不一致？"

### 步骤 4：基于结果迭代

询问读者 Claude 哪里搞错了或感到困难。表示打算修复这些差距。

回环到完善阶段以修复有问题的章节。

---

### 退出条件 (两种方法)

当读者 Claude 始终正确回答问题且未浮现新的差距或模糊之处时，文档就绪。

## 最终审查

当读者测试通过时：
宣布文档已通过读者 Claude 测试。在完成之前：

1. 建议他们自己进行最后一次通读——他们拥有此文档并对其质量负责
2. 建议再次检查任何事实、链接或技术细节
3. 请他们通过验证它是否达到了想要的影响

询问他们是否想要最后一次审查，或者工作是否已完成。

**如果用户想要最后一次审查，提供它。否则:**
宣布文档完成。提供一些最终提示：
- 考虑将此对话链接在附录中，以便读者可以看到文档是如何开发的
- 使用附录提供深度内容而不使主文档臃肿
- 随着收到真实读者的反馈更新文档

## 有效指导的技巧

**语气:**
- 直接且程序化
- 当影响用户行为时简要解释理由
- 不要试图"推销"这种方法——执行它即可

**处理偏差:**
- 如果用户想跳过一个阶段：询问他们是否想跳过这个并进行自由形式写作
- 如果用户看起来很沮丧：承认这比预期的要长。建议加快速度的方法
- 始终给予用户调整流程的代理权

**上下文管理:**
- 在整个过程中，如果提到的某事缺少上下文，主动询问
- 不要让空白积累——在出现时解决它们

**Artifact 管理:**
- 使用 `create_file` 起草完整章节
- 使用 `str_replace` 进行所有编辑
- 每次更改后提供 artifact 链接
- 切勿使用 artifact 进行头脑风暴列表——那只是对话

**质量优于速度:**
- 不要匆忙通过各阶段
- 每次迭代都应做出有意义的改进
- 目标是对读者真正有效的文档
