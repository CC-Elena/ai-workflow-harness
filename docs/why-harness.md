# Harness 的必要性与科学性

> **Thesis**: 大语言模型正在快速商品化，模型权重本身的竞赛边际收益递减。
> 决定 AI 辅助编程可靠性、可维护性、可扩展性的，是模型外围的 **Harness 工程层**——
> 权限门控、工具调度、上下文管理、子智能体隔离、生命周期 Hook。
> 这不是一家公司的工程偏好，而是多个独立团队在无交叉参考前提下**被迫收敛到的自然架构**。

---

## 一、问题背景：为何模型本身不足以支撑生产级软件工程

### 1.1 当前 AI 编程工具的能力边界

Claude Code、Codex 等工具在以下维度已经表现卓越：

- 单文件代码生成与补全
- 跨文件上下文理解与重构
- 基本错误定位与自我修复
- 自然语言需求到代码的端到端转换

但这些能力存在**结构性的天花板**，无法通过更大的模型或更长的上下文窗口解决：

| 局限性 | 根源 | 模型自身无法解决的原因 |
|--------|------|---------------------|
| **上下文衰减** | 对话历史线性增长，有效信息密度递减 | 模型没有「遗忘策略」，也无法决定哪些信息应该持久化 |
| **跨会话无记忆** | 每次对话从零开始 | 模型本身不具备项目级持久存储能力 |
| **局部最优决策** | 在单文件/单模块内做决策，无法感知全局架构约束 | 上下文窗口的物理限制，无法同时加载整个项目 |
| **行为不可靠** | 同一 prompt 可能产生不同行为 | 模型推理本身具有随机性，需要确定性切面来约束 |
| **执行过程不可观测** | 模型输出是代码，决策路径丢失 | 自回归生成范式不保留推理链路的显式记录 |

### 1.2 实证证据：Anthropic 的递归自我改进报告

Anthropic 在《When AI Builds Itself》（2026-05）中披露的数据，恰好证明了上述局限性：

- Claude 编写了 Anthropic **80%+ 的生产代码**（归因管道统计，保守估计）
- 工程师日代码产出是 2024 年的 **8 倍**
- 但报告同时坦承：「8 倍几乎肯定高估了真实生产力增益……代码行数衡量的只是数量，不是质量」

**关键洞察**：模型能力跃迁带来了效率提升，但同时也放大了「模型写出大量代码，但架构一致性、需求对齐、长期可维护性无人把关」的风险。Harness 正是为解决这个问题而存在。

## 二、科学性论证：收敛现象与形式化抽象

### 2.1 独立收敛：四个团队，同一种架构

MBZUAI 在 2026 年 5 月发表的学术论文（针对 Claude Code 源码的形式化分析）记录了一个令人震惊的现象：

> **Anthropic、OpenAI、Cursor、Devin 四个团队，在没有相互参考的前提下，各自独立设计的 Agent Harness，在功能边界上几乎完全重合。**

这不是巧合，也不是某家公司的专利设计。这是 **Agent 系统在生产化过程中被迫收敛到的自然形状**——类似于生物进化中的趋同进化。

四个独立团队最终都实现了以下核心组件：

```
权限门控（Permission Gating）
     ↓
工具调度（Tool Dispatch）
     ↓
上下文压缩（Context Compaction）
     ↓
子智能体隔离（Sub-Agent Isolation）
     ↓
Hook 生命周期（Hook Lifecycle）
     ↓
状态持久化（State Persistence）
     ↓
可观测性（Observability）
```

**科学意义**：当多个独立系统在相同约束下收敛到相同架构，这强烈暗示该架构是解决该类问题的**必要结构**，而非可选优化。

### 2.2 形式化抽象：Harness 的七组件模型

MBZUAI 论文将 Claude Code 的 Harness 抽象 formalize 为七个可复用组件：

| 组件 | 形式化定义 | 解决的工程问题 |
|------|-------------|----------------|
| UI Layer | 用户交互接口与权限确认界面 | 人机协同的决策边界 |
| Agent Loop | `AsyncGenerator<Event>` 驱动的状态机 | 模型推理与工具执行的编排 |
| Permissions | `deny → ask → allow` 三层决策树 | 模型行为的安全约束（确定性切面） |
| Tools | 注册-校验-执行-聚合流水线 | 模型能力的外延扩展 |
| State & Persistence | `mutableMessages[]` 作为唯一事实来源 | 会话状态的断点续传与审计追溯 |
| Execution Env | 沙箱隔离 + 工具调用 actual execution | 模型生成代码的安全执行环境 |
| Telemetry | 事件流上报与可观测性管道 | 系统行为的调试与优化依据 |

**核心论点**：这七个组件构成了 Harness 的**最小完备集**——缺少任何一个，系统都无法在生产环境中可靠运行。

### 2.3 Hook 系统的经典工程对应

Claude Code 的 Hook 系统设计（`matcher + chain + deny-wins`）直接对应 **Linux iptables 的 chain 模型**：

```
iptables: 规则链 → 匹配 → 决策（ACCEPT/DROP/REJECT）
Harness Hook: 生命周期事件 → matcher 匹配 → 决策（allow/deny/modify）
```

这不是隐喻，而是**经典系统工程模式在 Agent 领域的形式化迁移**。它证明了 Harness 设计不是凭空创造，而是有着深厚的系统工程学基础。

## 三、必要性论证：Harness 解决的具体问题

### 3.1 问题一：规划的可见性与审计追溯

**Claude Code/Codex 的现状**：规划的生成是隐式的，模型内部推理过程不透明，无法审计「为什么模型选择了这个方案」。

**Harness 的解决方案**：将规划固化为**显式的、结构化的 Plan 文档**，存入代码库版本管理：
- 每次规划决策可追溯（`git blames` 可查）
- Plan 文档作为模型执行的上下文注入，提高执行质量
- 规划过程本身可以被 Review、讨论、迭代

```
无 Harness:
  用户 prompt → 模型隐式规划 → 直接执行 → 产出代码
  （规划过程不可见，无法审计）

有 Harness:
  用户需求 → Spec → Plan 文档（显式、可审阅）→ 模型执行 → 验收 → 归档
  （全链路可回溯）
```

### 3.2 问题二：项目级知识的持久化与注入

**Claude Code/Codex 的现状**：每次对话从零开始，无法感知：
- 三个月前某个架构决策的原因
- 特定模块的隐含约束（时序要求、并发限制）
- 同一功能的多个实现版本及其兼容性要求

**Harness 的解决方案**：建立**项目级知识库**，在规划时自动检索并注入相关历史知识：

```
知识库内容：
  - 架构决策记录（ADR: Architecture Decision Records）
  - 已知陷阱与踩坑记录
  - 模块依赖关系图
  - 编码规范与命名约定

注入时机：
  Plan 生成前 → 检索相关历史知识 → 注入 Planner 上下文
```

### 3.3 问题三：Spec 验收的自动化

**Claude Code/Codex 的现状**：模型能写代码、能写测试，但**不会主动检查「Spec 中的每一条需求是否都被实现和验证了」**。

**Harness 的解决方案**：在 Plan 执行完毕后，自动执行 Spec 逐条验收：

```
Spec 验收检查表（自动化）：
  [ ] 需求点 1: 「导出按钮位于表格右上角」→ 对应组件存在？→ ✅/❌
  [ ] 需求点 2: 「CSV 文件编码为 UTF-8 BOM」→ 导出函数含 BOM 头？→ ✅/❌
  [ ] 需求点 3: 「超过 10 万行数据时显示进度条」→ 已实现？→ ✅/❌
```

这不是模型做不到，而是模型**不会主动做**。Harness 将这层保证固化为流水线的强制环节。

### 3.4 问题四：架构一致性的全局守护

**Claude Code/Codex 的现状**：模型倾向于做出局部最优决策——它不知道三个模块之外已经存在功能相同的工具函数，可能重复实现。

**Harness 的解决方案**：在 Plan 阶段植入**架构约束规则**，执行阶段验证：

```
架构约束示例：
  - 新增工具函数前，必须先搜索 codebase 中是否已有等价实现
  - API 路径必须符合 RESTful 命名约定
  - 新组件必须遵循既定的目录结构规范
  - 数据库访问必须通过既定的 ORM 层，禁止直接 SQL
```

## 四、Harness vs. 裸用 AI 编程工具：能力对比

| 维度 | 裸用 Claude Code / Codex | 基于 Harness 框架 |
|------|--------------------------|---------------------|
| **规划可见性** | 黑盒，隐式推理 | 白盒，显式 Plan 文档 |
| **规划复用** | 每次从零推理 | 历史 Plan 可复用、可进化 |
| **项目知识** | 无持久化，依赖 prompt 质量 | 框架内置项目规范、架构约束、知识库 |
| **质量门禁** | 无，模型自行判断 | 每个阶段有明确准入/准出检查 |
| **Spec 验收** | 不会主动执行 | 自动化逐条验收，强制通过方可进入下一阶段 |
| **审计追溯** | 不可追溯（对话历史即全部） | Spec → Plan → 实现 → 验收，全链路可回溯 |
| **断点续传** | 靠对话历史，会话丢失则不可恢复 | 每个阶段产物持久化，任意阶段可恢复执行 |
| **多人协作** | 各自对话，方案可能冲突 | Plan 文档作为团队对齐锚点 |
| **架构守护** | 无全局视野 | 约束规则注入 + 执行阶段验证 |

## 五、工程实证：上下文管理的量化分析

### 5.1 Claude Code 源码中的实证数据

对 Claude Code 泄露源码（~512K 行 TypeScript）的分析揭示了以下量化事实：

**上下文预算管理的必要性**：

| 问题场景 | 无 Harness 的后果 | Harness 的解决方案 |
|---------|------------------|---------------------|
| 对话历史无限增长 | 击穿 context cache，每次调用都付全价 | 静态/动态提示词分界 + 四个 cache_control 断点 |
| 探索性操作（如全文搜索） | 消耗 5-10 万 token，污染主上下文 | Sub-Agent 独立上下文窗口，只返回摘要给主 Agent |
| 上下文超限 | 模型拒绝响应，任务失败 | 五级压缩流水线（受控降级而非粗暴截断） |

**量化影响**（Anthropic 工程师采访数据）：
> 「主 Agent 的账单一大半花在『找路』上——加 Sub-Agent 之后，『找路』开销转移到不计费的临时上下文里。」

### 5.2 真实生产事故的证据

Claude Code 源码中记录了一次真实生产事故：

```
根因：Autocompact（自动上下文压缩）调用本身也是一次 LLM 调用。
     当上下文爆满到压缩 API 都拒绝时，重试无穷次只会无限计费。
后果：1,279 个会话连续 50+ 次自动压缩失败，
     每天浪费约 25 万次无效 API 调用。
修复：引入 MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3 熔断常量。
```

**启示**：模型自身的调用逻辑需要由 Harness 层的**确定性熔断机制**来约束。这是模型无法自我管理的一类问题。

## 六、AI 工程的三阶段演进框架

Faros AI（2026-05）提出了一个被广泛引用的分期框架，清晰刻画了 Harness Engineering 的历史定位：

```
Phase 1: Prompt Engineering（2022-2023）
  焦点：调教单次 LLM 调用
  代表方法：few-shot、CoT、system prompt 模板工程
  局限性：每次调用独立，无法处理多步骤任务

Phase 2: Context Engineering（2023-2025）
  焦点：把对的信息塞进上下文窗口
  代表方法：RAG、embedding 检索、长上下文模型、上下文压缩
  局限性：信息加载策略优化，但模型行为仍不可控

Phase 3: Harness Engineering（2025-至今）
  焦点：构建模型周围的执行环境与工程基础设施
  代表系统：Claude Code、Codex CLI、Cursor Agent、Devin
  核心洞察：模型正在快速商品化，但模型外层的 Harness
            ——权限门控、工具调度、上下文压缩、子智能体隔离、
              Hook 生命周期——才是真正决定 Agent 在生产环境
              能否长时运行而不漂移的关键。
```

**结论**：Harness Engineering 不是阶段 2 的替代品，而是**在 Context Engineering 基础上的必要演进**。没有好的 Context 策略，Harness 无处加载信息；但没有 Harness，再好的 Context 也无法转化为可靠的生产级软件工程输出。

## 七、总结：Harness 存在的根本理由

### 7.1 科学层面

1. **收敛现象**：四个独立团队无交叉参考收敛到相同架构，证明这是解决该类问题的**必要结构**。
2. **形式化基础**：MBZUAI 论文将 Harness 抽象为七个可复用组件，具有被验证的数学/工程严谨性。
3. **经典工程对应**：Hook 系统对应 iptables chain 模型，Hook 的 `deny-wins` 语义是确定性切面，这些都是经过时间检验的系统工程模式。

### 7.2 工程层面

1. **模型能力的互补而非替代**：Harness 不做模型擅长的事（代码生成、推理），只做模型做不好或不会主动做的事（规划审计、知识积累、架构守护、Spec 验收）。
2. **量化收益**：上下文预算管理直接降低 API 调用成本；Sub-Agent 隔离将探索性开销从不计费上下文转移；熔断机制防止无限计费。
3. **生产事故防护**：真实事故（1,279 会话无限重试）证明，纯模型调用的系统需要 Harness 层的确定性保护。

### 7.3 哲学层面

> **「模型提供智力，Harness 提供能力边界。」**
>
> 类比：模型是引擎，Harness 是传动系统、底盘、刹车和仪表盘。
> 没有引擎的车跑不起来，但没有传动系统和刹车的车——上路就是危险品。
