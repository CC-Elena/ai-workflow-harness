# 企业 AI Coding Agent 落地问题解决方案

讨论集中到企业真正需要落地的控制点：范围、验证、架构、成本、安全、治理和 ROI。

## 一句话结论

企业落地 AI Coding Agent 的关键，不是证明 AI 会不会写代码，而是建立一套能约束、验证、审计和衡量 AI 代码变更的工程系统。

推荐最小闭环：

```text
明确任务边界
  ↓
限制上下文和权限
  ↓
小步生成和修改
  ↓
自动验证和人工审查
  ↓
记录证据与成本
  ↓
失败复盘并反哺规则
```

## 1. 输出不可验证：不知道 AI 改了什么、有没有越界

### 典型现象

- AI 完成了任务，但顺手修改了任务范围之外的文件。
- 补丁看起来能跑，但掩盖了更深层的问题。
- PR 描述只有“已修复”，没有影响范围、测试证据和剩余风险。
- 合并后才发现改动触碰了权限、计费、部署或核心业务路径。

### 为什么危险

企业不是只关心代码是否能运行，还关心变更是否被授权、是否可追溯、是否能回滚。不可验证的 AI 输出会把风险转移到 review、测试和线上事故中。

### 解决方案

1. 任务开始前声明允许修改的文件、目录、接口和非目标。
2. 每次变更必须附带变更摘要、影响范围、验证证据和未解决风险。
3. 在 CI 或本地检查中加入范围外改动检测。
4. 生产路径、权限路径、计费路径、安全路径必须人工确认。
5. 保留操作日志和执行记录，便于回滚、追责和复盘。

### 在本项目中的落地动作

- 普通任务走 Lightweight Flow，先声明范围，再做最小修改。
- 中高风险任务使用 `specs/{feature}/spec.md` 明确范围和非目标。
- 在 `run-record.md` 中记录输入、修改文件、验证命令和风险。
- 使用 `npm run harness:check -- specs/{feature}` 检查记录是否覆盖实际变更。

### 验收证据

- PR 或最终说明中列出修改文件和未修改范围。
- 有真实 lint、typecheck、build、test 或页面验证证据。
- 高风险路径有人工确认记录。
- 若跳过验证，必须写明原因和风险，不能写成通过。

## 2. 架构一致性下降：局部能跑，长期难维护

### 典型现象

- AI 为了完成局部需求绕过既有模块边界。
- 新增重复组件、重复 Hook、重复 API 封装。
- 错误处理、状态管理、权限判断和数据流与项目惯例不一致。
- 一次性大范围重构后，review 很难判断架构影响。

### 为什么危险

AI 容易优化“当前任务能不能完成”，但企业系统还需要长期可维护性。架构一致性下降会让后续需求越来越慢，事故定位越来越难。

### 解决方案

1. 用 `AGENTS.md`、模块说明、架构决策记录和代码所有权文件给 Agent 稳定上下文。
2. 把任务拆成小步，避免一次性大范围重构。
3. 要求 AI 说明为什么这样改，以及为什么没有改其他地方。
4. 架构影响由资深工程师 review，而不是只看语法和测试。
5. 高风险设计先评审，再让 AI 写代码。

### 在本项目中的落地动作

- 创建或修改组件前，先查找已有组件和 Hook。
- 优先复用现有 `skills/`、`.ai/workflows/` 和 `docs/` 中的约定。
- 对跨模块、核心流程或规则变更，先说明影响面和非目标。
- 不把文档维护、小修小补自动升级成完整 Spec，避免流程噪声。

### 验收证据

- 变更说明能解释复用或不复用现有模块的理由。
- 没有新增明显重复的组件、工具函数或工作流规则。
- Review 中单独检查模块边界、依赖方向和长期维护成本。

## 3. 成本、限额和预算不可预测

### 典型现象

- 团队从个人或 Team 订阅升级到 Enterprise 后，成本结构突然变化。
- 大任务反复上下文读取、反复生成、反复失败，token 消耗失控。
- 所有任务都调用最贵模型，没有按任务复杂度路由。
- 管理层只看到 AI 工具账单，看不到成功任务数量和节省时间。

### 为什么危险

企业 AI 成本不是单纯的每百万 token 价格，而是席位费、上下文规模、失败率、返工率、等待时间和治理成本的组合。

### 解决方案

1. 建立内部 AI 网关或统一入口，记录模型、任务、token、耗时和结果。
2. 按任务类型选择模型：低风险文档和小改动不默认使用最高价模型。
3. 对重复任务做模板化和缓存，减少重复上下文消耗。
4. 记录每个任务的成功率、返工率、节省时间和验证成本。
5. 用“每个成功任务成本”衡量 ROI，而不是只看 token 单价。

### 在本项目中的落地动作

- 默认按最小 Skill 路由读取上下文，不全量读取 `.ai/`、`skills/`、历史 `specs/`。
- 普通任务走 Lightweight Flow，只有用户显式要求才进入 `/spec` 或 `/mini-spec`。
- 对每次复杂任务记录读取了哪些上下文、为什么读取、验证是否成功。

### 验收证据

- 每个任务有清楚的上下文读取范围。
- 大任务能看到任务拆分、验证结果和返工原因。
- 团队能按任务类型统计 AI 使用成本与成功率。

## 4. 安全边界进入供应链和 CI/CD

### 典型现象

- AI 会读取仓库、issue、PR、网页、配置文件和文档，其中可能夹带恶意提示。
- Agent 获得过大的文件系统、网络、密钥或部署权限。
- CI/CD 中的 Agent 根据不可信输入执行危险操作。
- 依赖、脚本、权限或部署配置被 AI 无意修改。

### 为什么危险

AI Coding Agent 不只是代码补全工具，它可能成为能读写仓库、执行命令、接触凭据和影响发布链路的自动化执行者。安全边界必须按执行者来设计，而不是按聊天工具来设计。

### 解决方案

1. 默认只给只读权限，写权限按任务临时授予。
2. 凭据隔离，禁止 Agent 直接读取生产密钥。
3. 在沙盒中运行生成、测试和验证步骤。
4. 对仓库、issue、PR、网页内容中的提示注入做安全扫描或人工复核。
5. 删除文件、迁移数据、修改权限、更新部署配置等动作必须人工确认。

### 在本项目中的落地动作

- 修改 `.codex/`、`.ai/`、`scripts/`、CI、包配置、核心配置、依赖和权限前先确认范围与风险。
- 不执行破坏性命令，除非用户明确要求并确认。
- 对网络访问、依赖安装和生产相关动作保持最小权限。

### 验收证据

- 高风险命令和高风险文件变更有确认记录。
- 没有把生产凭据、私有 token 或敏感配置写入文档和日志。
- CI/CD、依赖、权限相关变更经过人工 review。

## 5. 企业治理不能一刀切

### 典型现象

- 所有 AI 代理使用同一套审批规则，低风险任务被拖慢，高风险任务又约束不足。
- 文档代理、代码代理、运维代理、生产代理混用同一权限模型。
- 没有记录谁授权、做了什么、花了多少钱、产生了什么结果。

### 为什么危险

不同代理的风险等级、权限范围和业务影响差异很大。统一治理会同时制造低效和风险：该快的不快，该严的不严。

### 解决方案

1. 按风险分层治理：只读、低风险写入、高风险写入、生产影响动作。
2. 低风险任务自动执行，高风险任务引入人工批准。
3. 给每个 Agent 配置身份、权限、预算、审计和撤权机制。
4. 明确哪些任务可以自动合并，哪些任务必须代码所有者 review。
5. 建立 Agent 使用台账，记录授权、动作、成本、结果和失败复盘。

### 在本项目中的落地动作

- 轻量文档和小型修复默认走 Lightweight Flow。
- 复杂需求、跨模块变更或高风险路径建议使用 `/spec` 明确验收。
- 失败、验证不通过或人工大幅改动时，补 RCA 并反哺规则。

### 验收证据

- 每类任务有对应的执行流程和审批要求。
- 高风险路径不会被自动合并。
- 失败案例进入复盘，而不是被改写成成功记录。

## 6. ROI 难证明：通用助手不等于可衡量收益

### 典型现象

- 企业全员开通 AI Coding 工具，但无法证明交付更快或质量更好。
- 开发者感觉省时间，管理层看到的却是账单、返工和不确定风险。
- AI 使用集中在泛泛问答，没有落到可重复、可衡量的工程场景。

### 为什么危险

企业采购需要证明收益。没有基线和指标，AI Coding 很容易被看作成本中心，而不是工程能力建设。

### 解决方案

1. 先做 2 到 4 个低风险、高频、可衡量试点。
2. 为每个试点定义基线指标：PR 周期、返工率、缺陷逃逸率、review 时间、测试覆盖率。
3. 只在指标改善后扩大范围。
4. 把 AI Coding Agent 当作流程能力建设，而不是单个工具采购。
5. 培训开发者如何协作、审查和约束 Agent。

### 适合优先试点的场景

- 测试生成和补充。
- 小型缺陷修复。
- 文档同步和变更摘要。
- 迁移脚本和机械性重构。
- 内部工具原型。
- 安全扫描结果修复。

### 不适合首批试点的场景

- 权限、支付、生产数据和核心交易链路。
- 数据库不可逆迁移。
- 自动发布和无人值守合并。
- 需求边界不清的大规模重构。

### 验收证据

- 每个试点有上线前基线和上线后指标。
- 记录 AI 参与的任务数量、成功率、返工率和节省时间。
- 扩大范围前有真实样本，而不是只靠主观体验。

## 企业落地检查清单

开始使用前：

- [ ] 是否定义了 AI 可以改什么、不能改什么？
- [ ] 是否有任务范围、非目标和高风险路径说明？
- [ ] 是否有最小权限和凭据隔离？
- [ ] 是否明确哪些动作需要人工确认？

执行过程中：

- [ ] 是否只读取当前任务必要上下文？
- [ ] 是否小步修改，而不是一次性大范围重构？
- [ ] 是否保留变更摘要、命令输出和验证证据？
- [ ] 是否记录成本、耗时和返工情况？

合并或交付前：

- [ ] 是否通过 lint、typecheck、build、test 或对应人工验证？
- [ ] 是否检查范围外改动？
- [ ] 是否由代码所有者 review 高风险变更？
- [ ] 是否记录剩余风险和跳过验证原因？

推广前：

- [ ] 是否完成低风险试点？
- [ ] 是否有可衡量的收益指标？
- [ ] 是否有失败样本和 RCA？
- [ ] 是否把失败经验反哺到规则、模板或 Skill？
